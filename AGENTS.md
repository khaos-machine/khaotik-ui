# khaotik-ui

The Khaos-branded component library — the single home where the Khaos design
system is **built and maintained**, then **shared** with every Khaos app.
Successor to both `khaotik-3` (the token work) and `ucs` (the component +
composition work and its catalog).

There is **no generator**. Atoms, components and compositions are hand-authored
here in Svelte and shipped as `@khaos-machine/khaotik-ui`; the apps import them. The
UCS `.ucs.json` spec and its generator loop are retired (G78) — this repo *is*
the design→dev artifact, not an intermediate description of it.

## Layout

| Path | What |
| --- | --- |
| `tokens/` | Design tokens. `tokens.json` is the source of truth; `tokens.css` is generated by `build-tokens.py` (never hand-edited). `tokens-extra.css` is the seven-way StatusTone bridge; `utilities.css` carries `.eyebrow` / `.surface`, the classes the atoms render themselves — ship it or every eyebrow renders as body text. `parse.js` is the single parser that reads `tokens.css`, used by the catalog's brand screens — there were two, they drifted, and the drift shipped a crash. |
| `components/svelte/` | The atoms + compositions, hand-authored (Svelte, Ark UI). The `*.svelte.d.ts` and `index.d.ts` beside them are **generated** by `npm run build-types` and never hand-edited — `npm run check-types` fails if they drift from the components (D59). |
| `assets/placeholders/` | Pre-production artwork the kit ships so components have something honest to render before real imagery exists — twelve character silhouettes and the story cover. WebP, and the size matters: every consumer pays for them. Real art always wins; see the directory's README. |
| `apps/catalog/` | The component catalog — a Svelte + Tauri desktop app for playtesting atoms and compositions on devices against real KSPD data. |
| `docs/` | The live reference: `decisions.md` (the decision register — its highest id is a measurement, never a number written here — the command is in “The document set” above), `harvest-khaos-machine-tokens.md`, `tokens-to-ui.md`. |
| `scripts/` | The gates — `check-catalog-coverage.sh` (`npm run check-catalog`), `check-taxonomy.mjs` (`npm run check-taxonomy`) and `check-consumer.mjs` (`npm run check-consumer`), all run by `npm run check-coverage` along with the catalog's build. And `build-types.mjs` — the shipped TypeScript declarations (`npm run build-types` writes, `npm run check-types` fails on drift). Publishing the catalog site is the catalog app's own `apps/catalog/scripts/deploy-web.sh`. |
| `.claude/` | The agent toolkit for this repo — roles under `agents/`, plus `skills/` for svelte, tauri and MCP routing. Pruned to what a component library actually uses. |
| `.mcp.json` | Project-scoped MCP servers. `tauri` drives the running catalog through its dev-only bridge; see `.claude/skills/mcp-steering`. |

## Delivery ring — Outer

This repository is in the **Outer** ring. Work proceeds core outward: a ring must
be able to serve the ring outside it before that ring adopts, so Outer adopts
last, after every ring inside it is ready to serve it.

The ruling and the full ring membership live in the **workspace** ADR-0004,
"Delivery rings, and the documents that own them" (operator-ruled 2026-08-30),
one level up in `khaos.machine/docs/adr/`. **Deliberately not copied here.** A
branch from 2026-08-30 seeded a 185-line copy of it into this repository and
carried two re-sync commits in a single afternoon; measured 2026-09-09, the copy
had diverged from the root source again. That is the failure the workspace rule
already names — duplicated instructions rot apart, one file keeps issuing the
stale version, and an agent cites it with full confidence.

## Conventions

- **Warm-gray theme (D-005)**, not indigo/eggplant — the surfaces, text and
  borders point at the `warm` family in both light and dark. Indigo/grey are
  deprecated brand-mark primitives. Gold is reserved for the brand + primary
  actions only.
- **Dense native type + tight radii** (radius 4/6/8, hairline 1px, focus 2px).
- **StatusTone is seven-way** (`--tone-*`): success / warning / danger / info /
  neutral / accent / skipped.
- **D52 accessibility encoding**: a `div` + sibling buttons + `aria-hidden`,
  never a `<title>` (the cross-engine convention the atoms use).
- **Ark UI** (framework-agnostic) + Svelte bindings. No React.
- **Real data, never fabricated**: the catalog's demo data is fetched from the
  live khaosd daemon; gaps are reported, not papered over.

## Working

```sh
# the gates (0 clean / 1 gaps / 2 CANNOT RUN — a 2 is a red)
npm run check-coverage                # all four below, in order
npm run check-catalog                 # every export has a catalog fixture
npm run check-taxonomy                # every export is filed in a declared, labelled group
npm run check-consumer                # the package loads the way a consumer loads it
npm run check-compile                 # the catalog's build — it imports every export

# the component catalog (Tauri desktop app)
cd apps/catalog && npm run dev        # or: npm test, npm run build
cd apps/catalog && npm run dev:mcp    # desktop app with the MCP bridge live

# regenerate demo data (requires the khaosd daemon on 127.0.0.1)
apps/catalog/scripts/fetch-all.sh

# tokens
python3 tokens/build-tokens.py        # tokens.json -> tokens.css

# shipped TypeScript declarations — generated from the components, never hand-edited (D59)
npm run build-types                   # components/svelte/**/*.svelte -> **/*.svelte.d.ts
npm run check-types                   # red if a declaration has drifted from its component
```

## Releases

**Publishing is CI's, on GitHub-hosted runners — not something to run by hand.**
The repository is public, so its Actions minutes are free. Catalog credentials
(signing cert, Apple notarization, the updater key, the AWS keys that own the
buckets) are secrets; the npm publish uses trusted publishing and holds none.

One workflow *publishes*; two others check. `ci.yml` runs the gates on every
pull request and on push to `main`, and `catalog-release.yml` runs the same set
before it signs anything — both by calling `gates.yml`, so the PR gate and the
release gate cannot drift apart.

`gates.yml` runs **the catalog's test suite, then `check-coverage` (which chains
four gates), then `check-types`** — six checks, not the "three" this said for
months. `gates / gates` is a required status check on `main` with `strict: true`,
so a branch cannot merge without it and cannot merge stale. Before that existed, a PR's green
tick was two Socket Security dependency scans and nothing else (#87).

The catalog ships as a signed Tauri app
(`.github/workflows/catalog-release.yml` on tag `v*`), publishing updater
artifacts to `updates.loswf.com` via `apps/catalog/scripts/release.sh`. The
catalog's static web build goes to `khaotik-catalog.loswf.com` via
`apps/catalog/scripts/deploy-web.sh`, which `release.sh` itself calls as its last
step unless `--skip-release` — so the site publishes transitively through
`release.sh` rather than as a workflow step of its own. The library ships to
external apps as the `@khaos-machine/khaotik-ui` package (published to npm by
`lib-publish.yml` on each `lib-*` tag).

There were two workflows until D61. `storybook-deploy.yml` republished a
Storybook catalog to `khaotik-ui.loswf.com` on any push to `main`, and
`catalog-release.yml` deployed it again as its own last step; both are gone with
Storybook. `khaotik-ui.loswf.com` no longer resolves — issue #40 retired the
bucket, the CloudFront distribution and the DNS record on 2026-08-18, with no
redirect to the catalog.

**Published now: this line no longer states the numbers, because it was wrong
four times running.** It claimed catalog 0.15.0 against an unpublished draft;
library 0.12.0 against 0.16.0; library 0.16.0 against 0.18.0, within hours of
being corrected; and finally library 0.18.0 against 0.20.2, which stood for
four releases while the sentence one paragraph down told every reader not to
believe it.

**That last one is the argument for deleting the numbers rather than fixing
them a fourth time.** A warning attached to a stale fact does not stop the
fact being read — it only records that someone knew. The commands are the
answer, and they cannot go stale:

```sh
git tag -l 'lib-*' | sort -V | tail -1                                 # library
node -p "require('./package.json').version"                            # library
git tag -l 'v*' | sort -V | tail -1                                    # catalog
gh release view --json tagName --jq .tagName                           # what `latest` serves
```

The catalog ships as a signed, notarized DMG on the
[latest release](https://github.com/khaos-machine/khaotik-ui/releases/latest),
which must always be a `v*` tag — see the `--latest=false` rule below, and
`scripts/release-lib.sh`, which enforces it on the library path.

This block said "catalog 0.15.0" while `v0.15.0` was sitting as an unpublished
**draft**, invisible to `gh release view` and to every consumer, so the claim was
false in both halves at once. Both are Releases now, and the **workspace** `RULES.md` — one level up, section
"Releases and version pins" — is why:
publish a Release for anything another component consumes, and pin by version.
A bare tag is not a release, and a draft is not published.

The two version independently, and **each owns a tag prefix**, because for a
while they shared one:

| Prefix | Releases | Fires |
| --- | --- | --- |
| `v*` | the **catalog** | `catalog-release.yml` — signs, notarizes, publishes to `updates.loswf.com` and the CDN |
| `lib-*` | the **library** | `lib-publish.yml` — publishes `@khaos-machine/khaotik-ui` to npm (needs the `NPM_TOKEN` secret) |

**Cut a `lib-*` Release with `--latest=false`.** GitHub's `latest` is repo-wide
and last-publish-wins, so a library release with no flag silently takes the
pointer off the catalog — and `releases/latest` is what the link two paragraphs
up resolves through, and what a person checking "what version is the app"
lands on. It has fired **six** times: `lib-0.11.0` through `lib-0.15.0` each
held `latest` until the next catalog tag took it back, and `lib-0.20.0` held it
from 2026-09-21 until it was found by hand and restored to `v0.17.0` on
2026-09-22. The first five are inherited from the written record and are **not
independently verifiable** — the API exposes only the current `isLatest`, never
its history; the sixth was measured directly.

**This is enforced at publish, not remembered.** Both release paths assert the
pointer as they publish: `apps/catalog/scripts/release.sh` publishes the `v*`
release with `--latest`, and `scripts/release-lib.sh` passes `--latest=false`
and fails if the pointer moved. `scripts/check-latest-release.mjs` checks
`releases/latest` by hand. The `latest-pointer.yml` workflow that also ran it
on every release event and on a daily timer was removed on 2026-10-14
(operator: "make sure all scheduled certifications and extra workflows are
removed across the workspace so we're not spawing runs on timers or when other
CI runs are going"). A `gh release create` or `gh release edit --latest` typed
by hand now goes unwatched, so use the scripts.

**Tags are ANNOTATED from 2026-09-24 onward** — operator ruling, applying to
khaos-app and this repository. `gh release create` makes a **lightweight** tag,
so `scripts/release-lib.sh` now creates the tag object first and attaches the
release to it.

A lightweight tag is indistinguishable from an annotated one in `gh release
view` and in the web UI. The only thing that tells them apart is the ref's
object type, so the script asserts it rather than assuming:

```sh
gh api repos/khaos-machine/khaotik-ui/git/refs/tags/<tag> --jq '.object.type'
# "tag" = annotated · "commit" = lightweight
```

**Forward-only.** Every tag shipped before that date is lightweight and stays
that way; every `git describe` call site across the estate passes `--tags`,
which reads them. Nothing is retagged, because retagging moves refs consumers
may have pinned.

```sh
gh release create lib-X.Y.Z --target <full-sha> --latest=false --title ... --notes ...
```

`--target` needs the **full** SHA; an abbreviated one is rejected as
`Release.target_commitish is invalid`, which reads like a tag problem and is not.

`apps/catalog/scripts/release.sh` asserts `--latest` for the catalog path (#103),
and `scripts/release-lib.sh` is its counterpart for the library path — it passes
`--latest=false` and then **checks that the pointer actually held**, because
passing the flag and the pointer holding are two different claims. Use it rather
than `gh release create` by hand:

```sh
scripts/release-lib.sh --dry-run   # every guard, publishes nothing
scripts/release-lib.sh
```

The rule lived only in this file until 2026-09-22, and a rule that lives only in
prose is followed only by whoever reads it: the pointer was taken off the catalog
a **sixth** time by `lib-0.20.0`, and sat on a library marker with no DMG until it
was found and restored to `v0.17.0`.

Keep the prefixes apart. `v0.7.0` through `v0.9.2` are catalog tags from when
the catalog's version line ran through the same numbers the library is on now,
so `v0.9.0` already exists while the library is at 0.9.0 — tagging the library
`v0.9.0` was not merely confusing, it was taken, and any `v` tag ships a signed
release whether or not one was intended.

**Consumers pin a commit, not a branch.** This said "anything pinned to `main`
picks up library changes with no tag and no signal", and nothing pins to `main`
— `khaos-app/package.json` pins a bare SHA. That is the same no-signal problem
wearing different clothes: the pin was 24 commits and two minor versions stale
before anyone noticed, so D58's break and D59's shipped `.d.ts` had never
reached the client. Pin a `lib-*` tag instead; a version in the dependency
string is a thing a human can read.

`0.2.0` is the first deliberate break (D58), and the version had never moved
before it.

`updates.loswf.com/khaotik-catalog` (the updater feed the desktop app polls).
