# khaotik-ui

The Khaos-branded component library — the single home where the Khaos design
system is **built and maintained**, then **shared** with every Khaos app.
Successor to both `khaotik-3` (the token work) and `ucs` (the component +
composition work and its catalog).

There is **no generator**. Atoms, components and compositions are hand-authored
here in Svelte and shipped as `@khaos-machine/khaotik-ui`; the apps import them. The
UCS `.ucs.json` spec and its generator loop are retired (G78) — this repo *is*
the design→dev artifact, not an intermediate description of it.

## Layout

| `components/svelte/` | The atoms + compositions, hand-authored (Svelte, Ark UI). The `*.svelte.d.ts` and `index.d.ts` beside them are **generated** by `npm run build-types` and never hand-edited — `npm run check-types` fails if they drift from the components (D59). |

| `scripts/` | The gates — `check-catalog-coverage.sh` (`npm run check-catalog`), `check-taxonomy.mjs` (`npm run check-taxonomy`) and `check-consumer.mjs` (`npm run check-consumer`), all run by `npm run check-coverage` along with the catalog's build and `check-export-count.mjs`. ## Delivery ring — Outer

This repository is in the **Outer** ring. Work proceeds core outward: a ring must
be able to serve the ring outside it before that ring adopts, so Outer adopts
last, after every ring inside it is ready to serve it.

The ruling and the full ring membership live in the **workspace** ADR-0004,
"Delivery rings, and the documents that own them" (operator-ruled 2026-08-30),
one level up in `khaos.machine/docs/adr/`. **Deliberately not copied here.** A
branch from 2026-08-30 seeded a 185-line copy of it into this repository and
carried two re-sync commits in a single afternoon; measured 2026-09-09, the copy

## Conventions

- **Warm-gray theme (D-005)**, not indigo/eggplant — the surfaces, text and
  borders point at the `warm` family in both light and dark. Indigo/grey are
  deprecated brand-mark primitives. Gold is reserved for the brand + primary
  actions only.
- **Dense native type + tight radii** (radius 4/6/8, hairline 1px, focus 2px).
- **StatusTone is seven-way** (`--tone-*`): success / warning / danger / info /
  neutral / accent / skipped.
- **D52 accessibility encoding**: a `div` + sibling buttons + `aria-hidden`,
  never a `<title>` (the cross-engine convention the atoms use).
- **Ark UI** (framework-agnostic) + Svelte bindings. No React.
- **Real data, never fabricated**: the catalog's demo data is fetched from the
  live khaosd daemon; gaps are reported, not papered over.

## Working

```sh
# the gates (0 clean / 1 gaps / 2 CANNOT RUN — a 2 is a red)
npm run check-coverage                # every check below, in order (package.json)
npm run check-catalog                 # every export has a catalog fixture
npm run check-taxonomy                # every export is filed in a declared, labelled group
npm run check-consumer                # the package loads the way a consumer loads it
npm run check-compile                 # the catalog's build — it imports every export
npm run check-export-count            # every document stating an export count states the real one

# the component catalog (a web app; drive it in a browser, see .claude/skills/mcp-steering)
cd apps/catalog && npm run dev        # or: npm test, npm run build

# regenerate demo data (requires the khaosd daemon on 127.0.0.1)
apps/catalog/scripts/fetch-all.sh

# tokens
python3 tokens/build-tokens.py        # tokens.json -> tokens.css

# shipped TypeScript declarations — generated from the components, never hand-edited (D59)
npm run build-types                   # components/svelte/**/*.svelte -> **/*.svelte.d.ts
npm run check-types                   # red if a declaration has drifted from its component
```

## Releases

**Publishing is CI's, on GitHub-hosted runners — not something to run by hand.**
The repository is public, so its Actions minutes are free. The npm publish uses
trusted publishing and the Pages deploy uses the workflow's own `id-token`, so
neither holds a stored secret.

Two workflows *publish*, both on a `lib-*` tag: `lib-publish.yml` (npm) and
`catalog-pages.yml` (the catalog site). `ci.yml` and `gates.yml` check. `ci.yml`
runs the gates on every pull request, and `catalog-pages.yml` runs the same set
before it builds the site — both by calling `gates.yml`, so the PR gate and the
release gate cannot drift apart. `lib-publish.yml` does not call `gates.yml`.

`gates.yml` runs **the catalog's test suite, then `check-coverage`, then the
checks after it in that file** — read its `run:` steps for the list. This line
stated a count twice and was wrong both times ("three", then "six").
`main` is protected (operator ruling, 2026-11-03): changes arrive by pull
request (0 approvals), `gates / gates` must pass, admins are included, and
force-push and deletion are blocked. `strict` is **false**, so a branch can merge
behind `main`. When `main` has moved, re-run the gates before merging. Tag pushes
are not covered, so `release-lib.sh` pushing `lib-*` is unaffected. The repository
was re-created on 2026-10-30 without protection, and from then until this ruling
nothing enforced the gates. Read the current rules from the API, not from here:

```sh
gh api repos/khaos-machine/khaotik-ui/branches/main/protection
```

**One tag family, `lib-*`, releases everything.** The library ships to external
apps as the `@khaos-machine/khaotik-ui` package, published to npm by
`lib-publish.yml`. The catalog ships with it: `catalog-pages.yml` runs the
gates, builds the catalog's static web build with the Pages base path, and
deploys it to <https://khaos-machine.github.io/khaotik-ui/>. The catalog reports
the library's version, because `APP_VERSION` is read from the root
`package.json`.

The catalog was a signed desktop app with a release tag of its own until D95
retired it (#12, landed in #22). No desktop shell, signing, updater, MCP bridge
or S3/CloudFront deploy is left in the repository, and no workflow fires on any
tag but `lib-*`. Its catalog host and its updater feed were deleted on
2026-11-03; `CURRENT.md`, "Retired", records what went and what was kept.

There were two workflows until D61. `storybook-deploy.yml` republished a
Storybook catalog to `khaotik-ui.loswf.com` on any push to `main`, and
`catalog-release.yml` deployed it again as its own last step. Both stopped with
Storybook: `storybook-deploy.yml` was deleted and `catalog-release.yml` lost that
step. `catalog-release.yml` itself stayed, as the desktop release workflow,
until #22 removed it (D95). `khaotik-ui.loswf.com` no longer resolves — issue #40 retired the
bucket, the CloudFront distribution and the DNS record on 2026-08-18, with no
redirect to the catalog.

**Published now: this line no longer states the numbers, because it was wrong
four times running.** It claimed catalog 0.15.0 against an unpublished draft;
library 0.12.0 against 0.16.0; library 0.16.0 against 0.18.0, within hours of
being corrected; and finally library 0.18.0 against 0.20.2, which stood for
four releases while the sentence one paragraph down told every reader not to
believe it.

**That last one is the argument for deleting the numbers rather than fixing
them a fourth time.** A warning attached to a stale fact does not stop the
fact being read — it only records that someone knew. The commands are the
answer, and they cannot go stale:

```sh
git tag -l 'lib-*' | sort -V | tail -1                                 # library
node -p "require('./package.json').version"                            # library
gh release view --json tagName --jq .tagName                           # what `latest` serves: the newest lib-* release
```

The catalog has no version of its own to ask for: it reports the library's.

This block once said "catalog 0.15.0" while `v0.15.0` was sitting as an
unpublished **draft**, invisible to `gh release view` and to every consumer, so
the claim was false in both halves at once. Every `lib-*` tag is a Release, and
the **workspace** `RULES.md` — one level up, section "Releases and version
pins" — is why: publish a Release for anything another component consumes, and
pin by version. A bare tag is not a release, and a draft is not published.

**The newest `lib-*` release holds `latest`.** While the desktop catalog
existed, the library and the catalog each owned a tag prefix (`lib-*` and
`v*`), and a library release had to pass `--latest=false`: GitHub's `latest` is
repo-wide and last-publish-wins, so a library release with no flag took the
pointer off the catalog's DMG. That fired **six** times: `lib-0.11.0` through
`lib-0.15.0` each held `latest` until the next catalog tag took it back, and
`lib-0.20.0` held it from 2026-09-21 until it was found by hand and restored to
`v0.17.0` on 2026-09-22. The first five are inherited from the written record
and are **not independently verifiable** — the API exposes only the current
`isLatest`, never its history; the sixth was measured directly.

With one release family the rule inverted. `scripts/release-lib.sh` publishes
with `--latest` and then fails unless `releases/latest` is the new tag. The
`scripts/check-latest-release.mjs` hand check, and the catalog path's own
`--latest` assertion (#103), went with the desktop app. The `latest-pointer.yml`
workflow that also ran the hand check on every release event and on a daily
timer was removed on 2026-10-14 (operator: "make sure all scheduled
certifications and extra workflows are removed across the workspace so we're not
spawing runs on timers or when other CI runs are going"). A `gh release create`
or `gh release edit --latest` typed by hand goes unwatched, so use the script.

**Tags are ANNOTATED from 2026-09-24 onward** — operator ruling, applying to
khaos-app and this repository. `gh release create` makes a **lightweight** tag,
so `scripts/release-lib.sh` now creates the tag object first and attaches the
release to it.

A lightweight tag is indistinguishable from an annotated one in `gh release
view` and in the web UI. The only thing that tells them apart is the ref's
object type, so the script asserts it rather than assuming:

```sh
gh api repos/khaos-machine/khaotik-ui/git/refs/tags/<tag> --jq '.object.type'
# "tag" = annotated · "commit" = lightweight
```

**Forward-only.** Every tag shipped before that date is lightweight and stays
that way; every `git describe` call site across the estate passes `--tags`,
which reads them. Nothing is retagged, because retagging moves refs consumers
may have pinned.

A release created by hand with `--target` needs the **full** SHA; an
abbreviated one is rejected as `Release.target_commitish is invalid`, which
reads like a tag problem and is not.

`scripts/release-lib.sh` publishes with `--latest` and then **checks that the
pointer actually landed on the new tag**, because passing the flag and the
pointer holding are two different claims. Use it rather than `gh release create`
by hand:

```sh
scripts/release-lib.sh --dry-run   # every guard, publishes nothing
scripts/release-lib.sh
```

The `--latest=false` rule lived only in this file until 2026-09-22, and a rule
that lives only in prose is followed only by whoever reads it: the pointer was
taken off the catalog a **sixth** time by `lib-0.20.0`, and sat on a library
marker with no DMG until it was found and restored to `v0.17.0`.

**Consumers pin an exact npm version.** A version in the dependency string is
a thing a human can read. khaos-app once pinned a bare SHA, which is the same
no-signal problem as pinning `main`: the pin was 24 commits and two minor
versions stale before anyone noticed, so D58's break and D59's shipped `.d.ts`
had never reached the client. It pins an npm version now; read which one in
`khaos-app/package.json`, not here.

`0.2.0` is the first deliberate break (D58), and the version had never moved
before it.
