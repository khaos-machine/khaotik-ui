# Using the library

For a Svelte developer on another Khaos app who wants to adopt
`@khaos-machine/khaotik-ui` and get it right the first time. Ten minutes, start to
finish. Per-prop detail is not here — it ships in the components themselves and
shows up on hover in your editor. See §5, "Where the prop reference is".

Read the operational fact first, because it affects how you install:

> Install from npm and pin an exact version:
> `"@khaos-machine/khaotik-ui": "0.164.1"`. See
> [Versioning reality](#7-versioning-reality).

---

## 1. Install

Requires Svelte 5 — `package.json` declares `"peerDependencies": { "svelte":
"^5.0.0" }` and the components are written in runes (`$props`, `$state`,
`$derived`).

```jsonc
// package.json — pin to a commit, not to a branch. See §6.
"dependencies": {
  "@khaos-machine/khaotik-ui": "github:khaos-studio/khaotik-ui#<commit-sha>",
  "@ark-ui/svelte": "^5.23.0",
  "@phosphor-icons/web": "^2.1.2"
}
```

`@ark-ui/svelte` and `@phosphor-icons/web` are declared as `dependencies` of
the library itself, so a package manager will install them for you. The
in-repo consumer (`apps/catalog/package.json`) declares them directly anyway;
doing the same makes the versions you actually compile against explicit.

The package ships **uncompiled `.svelte` source** — no compile step, no
`dist/`, and no `svelte` export condition in `package.json`. Your bundler must
compile `.svelte` files coming out of `node_modules`
(`@sveltejs/vite-plugin-svelte` does this by default for the resolved paths).
The one generated thing we ship is the TypeScript declarations, which sit
*beside* the source rather than replacing it — see
[TypeScript](#typescript-the-declarations-are-generated-not-written).

The `exports` map is four entries:

```jsonc
"exports": {
  "./tokens/*":            "./tokens/*",
  "./components/svelte":   { "types": "./components/svelte/index.d.ts",
                             "default": "./components/svelte/index.js" },
  "./components/svelte/*": { "types": "./components/svelte/*.d.ts",
                             "default": "./components/svelte/*" },
  "./assets/*":            "./assets/*"
}
```

So: tokens by file, components via the barrel, a single component by path, or a
shipped asset. There is no root export — `import … from '@khaos-machine/khaotik-ui'`
will not resolve.

### TypeScript: the declarations are generated, not written

Every component ships a `X.svelte.d.ts` next to its `X.svelte`, plus an
`index.d.ts` for the barrel, generated by `npm run build-types` from the
components' own `$props()` via `svelte2tsx` — the same engine
`@sveltejs/package` uses. So this is checked, at the call site:

```svelte
<script lang="ts">
  import { SceneTable } from '@khaos-machine/khaotik-ui/components/svelte'
</script>
<SceneTable {scenes} onselect={pick} selected={42} />
<!--                                  ^ Type 'number' is not assignable to
                                        type 'string | undefined'. -->
```

**Delete any hand-written `declare module '@khaos-machine/khaotik-ui/components/svelte'`
block you are carrying.** It shadows these declarations, and the shape everyone
wrote — `Component<Record<string, unknown>>` — checks no prop at all while
drifting out of date silently (issue #21).

Two things to expect when you first turn it on:

- **A prop with no default is required.** `onSelect`, `oninput`, `onSeek` and
  the rest are declared without defaults in the components, so `<FilterField />`
  now errors with *"Property 'oninput' is missing"*. That is the intended
  reading — a filter with no `oninput` renders and does nothing — but it will
  surface at adoption, not gradually.
- **Object-shaped props are `any[]` / `any`.** The sources are JavaScript, so
  the inferred types are as specific as the defaults allow: `paginate?: boolean`
  and `selectedId?: string` are real, `scenes?: any[]` is not. Narrowing those
  means annotating the components, which is a separate change.

The declarations are committed, and `npm run check-types` regenerates them into
a temp directory and fails on any difference — so they cannot go stale against
the components they describe. It runs in CI ahead of both publish paths. The
`types` condition on `./components/svelte/*` maps `*` to `*.d.ts`, which is
correct for the `.svelte` files that make up the public surface; the internal
`components/svelte/lib/*.js` helpers are not part of it and are not typed
through that entry.

## 2. The three stylesheets (all three are required)

```js
import '@khaos-machine/khaotik-ui/tokens/tokens.css'        // the palette + type + space, both modes
import '@khaos-machine/khaotik-ui/tokens/tokens-extra.css'  // the seven-way --tone-* StatusTone bridge
import '@khaos-machine/khaotik-ui/tokens/utilities.css'     // the utility roster below
```

### The utility roster

Four classes, and the sheet is the only place they are declared — `tokens/parse.js`
parses `utilities.css` into a roster that this table, the catalog's BrandKit →
Type → Utilities screen, and the kit's own components all read. Add a rule there
with a prose comment and a `@kind` annotation and it appears in all three; add it
anywhere else and the gates fail.

| Class | Kind | What it is |
| --- | --- | --- |
| `.surface` | sample | A raised background, not a card. Native sections sit flat on the canvas; separation comes from the header and spacing, never a floating border. |
| `.eyebrow` | sample | The uppercase caption that labels a section or metric. Five shipped components render it themselves. |
| `.note` | sample | A quiet line of supporting copy beside the thing it explains — body size, not caption; the inline sibling of `EmptyState`'s description. |
| `.visually-hidden` | demo | Takes an element out of sight while leaving it in the accessibility tree. `Icon` is `aria-hidden` by contract, so this is how an icon-only control gets a name a screen reader can announce. |
| `.ui-range` | demo | A range input, drawn: one hairline track and a small thumb. `accent-color` alone leaves WebKit's own track, a tall white bar on a dark surface. The kit's sliders and scrubbers carry it; put it on any `<input type="range">` of your own. |

`kind` is the catalog's treatment, not a CSS distinction: `sample` classes get a
rendered specimen, `demo` classes get a demonstration of the class working —
absence is the observable, and showing absence beats faking a sample.

`utilities.css` is **not** optional polish. Shipped components render
`class="eyebrow"` themselves — `SectionHeader`, `LabeledPill`, `MetaStrip`,
`ResourceCatalog` and others. Without the sheet every
eyebrow in the library degrades to plain body text: still there, silently
wrong. That is the reason the class lives in the kit rather than in each app
(`tokens/utilities.css:1-20`).

`tokens-extra.css` is the same story for colour: `StatusPill`, `MetricCard`
and the rest style themselves off `--tone-success`, `--tone-warning`, … which
are defined only in that file. Skip it and the tones fall back to
`currentColor`.

### Phosphor icons need their own CSS

`Icon.svelte` emits `<i class="ph ph-<name">` / `ph-<weight> ph-<name>` — it
does not bundle a font. Import the kit's icon stylesheet once:

```js
import '@khaos-machine/khaotik-ui/assets/icons/phosphor.css'
```

It carries Phosphor's `regular` and `fill` weights, which cover every glyph the
components render, as woff2 only: 279 KB in your build. Phosphor's own
stylesheets (`@phosphor-icons/web/regular`, `/fill`) also list woff, ttf and
svg, so a bundler copies 7.5 MB of fonts no browser fetches.

`Icon`'s type still accepts all six weights (`regular|thin|light|bold|fill|duotone`).
For another weight, import its stylesheet from `@phosphor-icons/web` as well
(`import '@phosphor-icons/web/bold'`). A `weight` whose stylesheet is not loaded
type-checks, renders, and silently falls back to whatever is loaded.

### The kit ships placeholder artwork, and your bundler must handle it

`Portrait` imports twelve WebP silhouettes from
`assets/placeholders/silhouettes/` — `{female, male, nonbinary, unknown} ×
{young, adult, senior}` — so a character with no picture still renders as a
figure rather than a glyph. 108 KB total, and only what you render is fetched.

That means **your bundler must resolve image imports from `node_modules`**, the
same way it already compiles `.svelte` from there. Vite does by default.

They are placeholders, not final art, and the precedence is designed for the
transition:

1. `src` — real or generated art you already hold. Renders untinted.
2. `figureFor` — your own placeholder set, if you would rather use it.
3. the kit's silhouette for the bucket.
4. the glyph — `scene` and `location`, which have no figure set.

`src` wins **per Portrait**, not globally, because the engine generates art one
character at a time: a project with art for four of twenty characters renders
those four for real and the rest as placeholders, in the same list, with no mode
switch on your side.

```svelte
<!-- override some buckets, inherit the rest -->
<Portrait {name} {gender} {age} figureFor={({ gender }) => myArt[gender] ?? null} />
```

`figureFor` is accepted by `Portrait` and `Gallery`, which forwards it to each
portrait.

### One thing the library does not do: paint the page

`tokens.css` only defines custom properties. Nothing in it styles `body`, so
the background and base text colour are yours. The catalog's entire consumer
CSS layer is four rules (`apps/catalog/src/app.css`):

```css
:root { font-family: var(--font-sans); line-height: 1.5; color-scheme: light dark; }
body  { margin: 0; color: var(--text-primary); background: var(--surface-base); }
```

Copy that and you are on the theme.

## 3. Theming

**Dark is the default.** `tokens.css` emits the semantic layer under
`:root, .dark, [data-theme="dark"]` (line 162) and overrides a subset under
`html[data-theme="light"]` (line 227). The light block wins on specificity
(0,1,1), not source order — so you flip modes by setting one attribute on
`<html>`:

```js
document.documentElement.dataset.theme = 'light'  // or 'dark'
```

Seed it before first paint if you care about a flash — the catalog does exactly
this from its app shell (`apps/catalog/src/App.svelte:39`).

### Use the semantic tokens

| Family | Members (verified in `tokens/tokens.css`) |
| --- | --- |
| `--surface-*` | `base`, `raised` |
| `--text-*` | `primary`, `secondary`, `tertiary`, `brand` |
| `--action-*` | `primary`, `primary-border`, `primary-pressed`, `on-primary`, `disabled`, `on-disabled` |
| `--border-*` | `default`, `hairline`, `focus` |
| `--status-*` | `normal` / `warning` / `alarm` / `offline` / `accent` / `skipped`, each `-fg` / `-bg` / `-mark` |

Plus type (`--body-md-*`, `--caption-*`, `--label-sm-*`, `--data-md-*`,
`--data-input-*`), `--font-sans` / `--font-mono`, `--spacing-*`, `--radius-*`.

The seven-way StatusTone scale, from `tokens/tokens-extra.css`:

```
--tone-success  --tone-warning  --tone-danger  --tone-info
--tone-neutral  --tone-accent   --tone-skipped
```

Every `tone` prop in the library (`StatusPill`, `MetricCard`, `LabeledPill`)
takes one of those seven words.
Two of them are still aliases onto other tokens because the BrandKit has not
named them yet — `--tone-info` rides `--st-provis-fg` and `--tone-neutral`
rides `--text-secondary` (`tokens-extra.css:5-14`). They work; they are just
not final.

### Do not use primitive tokens in app code

`--warm-950`, `--gold-400`, `--green-450`, `--red-300` and friends are the raw
ramp. They are **mode-invariant** — they hold the same value in dark and in
light, because the semantic layer is what flips. Reach for `--warm-950` in an
app and you have hardcoded a dark-mode colour that will still be near-black on
a light background. Always go through the semantic token.

(The one deliberate exception inside the library is `--scrim`, which points at
a primitive on purpose: a scrim darkens in both modes. `tokens.css:275-280`
explains it.)

## 4. What is in the box

Every export from `components/svelte/index.js`. The tables below group them for
reading. **The authoritative placement is elsewhere** — the `section` / `group`
fields in `apps/catalog/src/fixtures.js`, which drive the catalog's sidebar and
are gated by `npm run check-taxonomy`.

The two do not line up one-to-one: the catalog files these across thirteen groups
under five sections, and a few land somewhere you would not guess from the
headings here (`StoryAtlasToolbar` sits under Screens → Story · Atlas, where
Khaos App renders it; `Icon` is BrandKit). When the two disagree, `fixtures.js` is right.

```js
import { StatusPill, SelectableRow, CharacterTable } from '@khaos-machine/khaotik-ui/components/svelte'
// or, one file:
import StatusPill from '@khaos-machine/khaotik-ui/components/svelte/StatusPill.svelte'
```

| --- | --- |

| `SectionHeader` | Eyebrow over a title, with an optional trailing control. |

| `ServiceStatusList` | The on-device engines from `GET /api/services`. Renders the daemon's own `name` — **no label table** — and shows start/stop disabled where a consumer is not permitted to call them. |

`Menu`, `SegmentedControl`, `Toggle` and `ConfirmDialog` are **adopted, not
authored** (D39/D50):
the ARIA pattern, focus management, roving arrow keys, typeahead, and — for
`Toggle` — the checkbox semantics, the form-carrying hidden input and the
disabled handling all come from Ark UI. Do not reimplement around them.

`ConfirmDialog` is a confirmation rather than a general Dialog on purpose. A
general modal is a container, and would leave every consumer to invent its own
question, button order and destructive treatment — which is how one dialog ends
up reading three ways across three surfaces. It reports intent and does **not**
close itself on confirm, so a mutation that fails can keep the dialog up and say
why.

`Toggle` is a switch rather than a styled checkbox on purpose: it applies as you
flip it, where a checkbox promises a pending change you submit later. Its `hint`
renders in the UI rather than as a tooltip — a tooltip hides the explanation from
the person who opened a settings screen to find out what the setting does.

### Scene read progress

`SceneReadStatus` renders a host-declared workflow (`running`, `partial`, `indeterminate`,
`completed`, or `retired`), its completed-line retention/reuse/remaining counts and message.
Only `resume.allowed` offers Resume; remaining counts do not create eligibility.
`onResume(workflowId)` reports one explicit intent to resume that existing workflow,
while `resuming` expresses host admission. It never executes work or chooses
which lines to regenerate. Keep `TakeList` for completed audio and its existing controls.

The contract is declared in [SceneReadStatus](../components/svelte/SceneReadStatus.svelte). Gap #326 owns this
presentation extension. The catalog has no captured workflow and displays that
absence; unit fixture results are not provider or workflow execution certificates.

## 5. The conventions that will bite you

### The story's tables select by id

```
SceneTable     scenes={}      selected={}  onselect(id)   // matched: selected === scene.id
CharacterTable characters={}  selected={}  onselect(id)   // matched: selected === character.id
```

Both pass the row's id, never the row: the host looks the record up. An empty
`selected` selects nothing, even where khaosd sent rows with empty ids.

### Callbacks are optional, and calling them is optional-chained

Every handler is invoked as `onSelect?.(…)`, `onEditField?.(…)`,
`onsave?.(…)`. A component rendered with no handler renders fine and does
nothing — it will not throw. Convenient in a catalog fixture; a silent trap in an
app.
If a row highlights on hover but nothing happens on click, check that you
passed the handler at all before you go looking for a bug.

### Editable fields report the value

`EditableField` reports `onsave(value)` and `oncancel()`, lowercase, with no
field name (`EditableField.svelte:7`). The host knows which field it rendered,
so it attaches the identity and the path itself.

### The D52 accessibility encoding — do not "fix" it

The atoms use a plain `div`/`button` structure with `aria-hidden` on the
visible text and the accessible name on the control, never an SVG `<title>`.
`SelectableRow` is the canonical example:

```svelte
<button type="button" aria-label={title} aria-current={selected ? 'true' : undefined}>
  <span class="selectable__title" aria-hidden="true">{title}</span>
  …
</button>
```

The text is visually present and hidden from assistive tech precisely because
the button already carries it as its name; the alternative is a screen reader
reading the row twice. It looks wrong at a glance and it is correct. It is a
cross-engine convention (`AGENTS.md`, "Conventions"), so if you wrap or extend
these components, follow it — and note the companion rule: D52 covers *naming*
and *hiding inner text*; it does not excuse dropping **state**, which is why
`aria-current` is there.

`Icon` is `aria-hidden` for the same reason — the surrounding control names
itself.

### Where the prop reference is

Not this document — your editor. Every component carries a JSDoc `Props` typedef,
and `npm run build-types` compiles it into the shipped `*.svelte.d.ts`. Hover a
prop and you get its description and its real type:

```svelte
<StatusPill text="Analyzed" tone="success" />
<!--                        ^ hover: "Maps to `--tone-*`. A value outside the
                              seven renders with no tint rather than falling
                              back." — typed as the seven StatusTone strings -->
```

Because the types are real unions rather than `string`, a typo is a build error
in a consuming app: `tone="succes"` and `thumbKind="charater"` both type-checked
before this and do not now.

The declarations are generated and committed, and `npm run check-types` fails if
one has drifted from its component — so the reference cannot go stale the way a
separate document can. This replaced a published Storybook whose `argTypes`
descriptions were the reference (D61); the prose moved onto the components, which
is further than the site reached, since it now arrives wherever the package is
installed.

## 6. Migrating to 0.2.0 (D58)

`0.2.0` is the first deliberate breaking change to `@khaos-machine/khaotik-ui`
(`docs/decisions.md`, row **D58**). The four lists it renamed have since retired;
this section stays for a consumer upgrading across it. Two renames:

```svelte
<!-- before (0.1.0) -->
<SceneList     {scenes}     selectedId={sceneId}  onSelectScene={pick} />
<DialogueList  {dialogues}  selectedId={lineId}   onSelectDialogue={pick} />
<CharacterList {characters} selectedId={name}     onSelect={pick} />
<LocationList  {locations}  selectedId={name}     onSelect={pick} />

<!-- after (0.2.0) -->
<SceneList     {scenes}     selectedId={sceneId}  onSelect={pick} />
<DialogueList  {dialogues}  selectedId={lineId}   onSelect={pick} />
<CharacterList {characters} selectedKey={name}    onSelect={pick} />
<LocationList  {locations}  selectedKey={name}    onSelect={pick} />
```

- `onSelectScene` → `onSelect`, `onSelectDialogue` → `onSelect`. The majority
  spelling won: `CharacterList`, `LocationList`, `SceneRow` and `DialogueRow`
  already used `onSelect`.
- `selectedId` → `selectedKey` on `CharacterList` and `LocationList` only.
  `SceneList` and `DialogueList` keep `selectedId` because theirs really is an
  id.

Both old names fail **silently**: an unknown prop is just ignored by Svelte, so
a missed rename produces a list that never highlights and never calls back
rather than an error. Grep for `onSelectScene`, `onSelectDialogue` and
`selectedId=` in your app and check each `selectedId` against the table in §5.

D58 also records the reversal condition: if the churn ever costs more than the
asymmetry, the old names come back as deprecated aliases rather than the rename
being undone.

## 7. Versioning reality

The library is published on npm as `@khaos-machine/khaotik-ui` (Apache-2.0).
Every `lib-*` tag publishes one version through `lib-publish.yml`, and that
version is the release. The catalog app versions independently under `v*`, so
don't read one version from the other.

**Pin an exact version** and upgrade deliberately. A range picks up a breaking
change with no warning, the way D58's rename once reached a consumer pinned to
`main`:

```jsonc
"@khaos-machine/khaotik-ui": "0.164.1"
```

On upgrade, read the new rows in `docs/decisions.md` — that register is where
breaking changes are actually recorded — and diff
`components/svelte/index.js` for added or removed exports.

### StoryPlayer transport

`currentTime` determines playback activity; `selectedElementId` is the host's
intentional selection. Pass an empty selection when following the playhead.
Activity uses a fill, while the selected event has an outline and `aria-pressed`.
Do not pass the active event as `selectedElementId`: that makes playback appear
to change the user's selection. Keyboard focus retains its separate focus ring.

`onStop`, `onPreviousScene`, `onNextScene`, `onPreviousBeat` and `onNextBeat`
are optional host intents; omitted callbacks omit their buttons. Beginning/end
controls seek through `onSeek`. The playhead supports Left/Right (one second),
Shift+Left/Right (ten seconds), Home and End. Its 18px pointer target and ruler
support continuous scrubbing even after horizontal scrolling.

`onScrubStart` / `onScrubEnd` bracket pointer gestures, including cancellation,
blur and destruction. The host owns whether audio pauses and resumes. Automatic
playhead following is suspended during a drag so the track does not move beneath
it. See issue #389 for the interaction acceptance cases.

### ScreenplayEditor

A controlled screenplay editing surface. Supply a `document` with stable scene
and block identities, draft `title`, `page` and `texts` maps, and the selected
scene or `title-page`. `ontext(id, value)`, `ontitle(value)` and
`onpage(key, value)` change host-owned drafts; `onsave` requests a commit.
The host supplies `loading`, `saving`, `dirty`, `error`, `notice`, undo/redo
availability and callbacks. Keep failed drafts and preserve unfamiliar title-page
keys. The component performs no parsing, persistence or media generation.
